# v3.2.1 插件化架构设计草案

> 历史开发记录。v3.2.2 已整理为正式版本，当前行为与验证见 [正式验收](v3.2.2-validation.md) 和 [图文使用说明](../versions/v3.2.md)。

状态：已采纳并完成三个内置插件的首轮实现，内部接口继续验证，尚未对外冻结。日期：2026-10-11。开发分支：`dev/v3`。

本文是内部架构与验收方案，不是插件开发手册，也不表示第三方插件安装接口已经开放。用户已同意按此方案实施，应用开发版本为 v3.2.1；接口名和数据结构在最终验收后才能冻结。尚未修改任何 GitHub 发布或既有标签。

## 1. 版本目标和边界

把音乐控制、系统通知、Codex 信息改为三个内置插件，使用同一套注册、生命周期、状态、页面、命令、提醒和设置接口。后续增加待办、笔记或时间插件，不应再修改菜单中的功能分支。

插件化是架构调整，不是视觉重做。保留 v3.1.2 的圆角胶囊、固定设置入口、悬停预览与点击固定、内容分页滚动吸附、页面标题吸顶、边缘调整大小、字幕和隐私模式。

角色动画、角色导入、语音播放、角色预览与撤销重做、窗口定位和开机启动仍属于宿主核心。本版本不把这些基础功能一起迁移成插件，也不新增 AI 调用。

建议 v3.2.1 先交付三个内置插件与接口验证。第三方安装包、插件市场、自定义 HTML 页面及执行外部脚本不在默认交付范围；以后开放时仍复用本次契约，但必须另行完成安全设计。

## 2. 现状与需要解除的耦合

当前已有扩展分层雏形，但不是可调用的插件系统：

- `src/features/types.ts` 把功能 ID 固定为 music、notifications、codex，状态字段也是三种功能专用结构。
- `src/extensions.ts` 直接判断三种入口与渲染方法；添加第四种功能还需要修改菜单。
- `src/features/settings.ts` 直接列出三个功能和对应设置。
- `electron/extensions/preload.cjs` 提供专用的 media、dismiss 等调用。
- `electron/extensions/extension-service.mjs` 集中承担设置、媒体、通知、Codex 启停、去重和提醒。
- 音乐、通知和 Codex 进程探测共用一个 Windows 桥接进程，不能简单为每个插件复制一份服务。

已有 `docs/EXTENSIONS.md` 只描述方向。本文进一步收敛方案；正式确认后再统一旧文档，避免提前把提案当成 SDK。

## 3. 三层结构

```text
插件注册表 → 插件宿主 → 统一菜单 / 内容页 / 角色字幕 / 角色管理器
                 ↕
           三个内置 Provider
                 ↕
           受控能力代理
                 ↕
  Windows 媒体与通知桥接 / Codex 只读适配器 / 插件独立存储
```

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| 宿主 | 注册、授权、启停、统一 UI、隐私、已读、提醒队列、设置和诊断 | 理解某个播放器或服务的协议 |
| 插件 Provider | 获取自己的领域数据，将数据转换为页面与事件，处理声明的命令 | 操控角色窗口、注入 HTML、改变菜单交互 |
| 能力代理与适配器 | 访问系统或服务、权限检查、共享连接、超时和资源释放 | 决定菜单样式与提醒文案布局 |

内置插件也走统一接口，不能继续在宿主保留“如果是 music 就特殊调用”的捷径。可信内置适配器可以保留平台专用代码，但不直接出现在通用渲染器中。

共享桥接采用能力订阅计数：按当前启用插件的需要合并 music、notifications、codexProbe 配置，最后一个订阅释放后才停止进程。禁用通知不应中断音乐，禁用音乐不应中断 Codex 检测。

## 4. 统一契约

### 4.1 插件清单 Manifest

建议保留以下字段，具体 schema 在确认后实现：

| 字段 | 含义 |
| --- | --- |
| id / name / version | 稳定唯一 ID、显示名称、插件版本 |
| apiVersion / configVersion | 接口兼容版本、插件配置版本；与应用版本分别管理 |
| entry / icon / description | Provider 入口、受控图标、功能说明 |
| permissions | 需要的能力；有效权限为声明与实际授权的交集 |
| commands | 命令 ID、参数 schema、所需权限；未声明命令不能调用 |
| settingsSchema | 宿主可渲染的设置项、默认值和范围 |
| compatibilityNotes | 在角色管理器显示的兼容条件、限制与排查说明 |
| entryVisibility | when-available 或 when-enabled，控制入口显示，不控制服务启停 |

内置 ID 建议为 `workshop.music`、`workshop.notifications`、`workshop.codex`。宿主登记来源为内置或外部，不能相信插件自称“内置”。显示名称可以变化，ID 不能随之变化。

“已启用”和“入口可见”分开：音乐没有会话时隐藏入口，但监测仍运行；通知已启用时，即使没有新消息也保留铃铛入口。

### 4.2 生命周期

`activate(context)` 返回一个插件实例，由宿主管理实例，不使用跨实例共享的模块全局状态。

| 接口 | 责任 |
| --- | --- |
| activate(context) | 获取已授权能力并启动订阅；context 带取消信号与清理注册机制 |
| getSnapshot() | 返回当前声明式页面状态，不直接访问或修改界面 |
| context.publish(snapshot) | 数据变化时发布状态，宿主校验、合并并限频 |
| execute(commandId, payload) | 执行已声明且通过宿主校验的命令 |
| onSettingsChanged(config) | 可选；响应自己配置的变化，不能修改其他插件配置 |
| context.emit(event) | 提交提醒事件，是否显示由宿主决定 |
| dispose() | 停止定时器、释放订阅、撤销回调及适配器租约；可重复调用 |

界面已读由宿主管理。插件如需获知已读，可以订阅宿主的受控回执事件；回执不自动代表外部聊天已读，也不授权插件删除系统通知。

宿主运行状态为 disabled、starting、active、stopping、failed、incompatible。插件内容状态为 waiting、ready、degraded、error。两者分开，例如 Codex 插件已启动，但正在等待 Codex 程序运行。

每次启用产生新的 activationEpoch。禁用时立即撤销能力，取消未完成操作；旧实例迟到的 publish、emit 和命令结果全部忽略。清理失败不能使其他插件不可用。

### 4.3 状态与页面

插件只发布可序列化数据。宿主给消息附加 pluginId、activationEpoch、revision，插件不能自行伪造其他插件的身份。

```text
PluginSnapshot
  available          当前是否有可展示内容
  status / message   内容状态与安全的解释文案
  updatedAt          最近成功更新的时间
  pages[]
    id               稳定页面 ID
    title / subtitle / icon
    source           来源名称与来源 ID
    readKey?         此版本内容的已读键
    blocks[]         宿主组件描述
```

页面标题属于当前页，而不是始终写插件名称。通知页标题可以是 QQ 或 GPT；音乐页标题可以是具体播放器；Codex 分为“额度”和“最近任务”。

宿主保留当前页面 ID 和每页内容滚动位置，后台刷新不能把用户送回第一页。相同页面有新内容时，由新 readKey 区分；不能只按页面 ID 判断已读。

初期组件建议为 text、image、group、list、metric、progress、timeline、button、status、time。它们覆盖现有功能，样式和交互统一由宿主提供。图片通过经过验证的资源引用传递，不让插件向页面插入任意 URL、脚本或 HTML。

时间戳统一为 UTC ISO 8601；播放位置和时长统一为毫秒；进度比例明确为 0–100。旧媒体接口中的秒数由适配器转换。未知值用 null，不使用 0 假装“余额为零”或“歌曲时长为零”。

### 4.4 命令

UI 使用同一条调用：`execute(pluginId, commandId, payload)`。宿主检查调用窗口、真实插件实例、启用状态、命令声明、参数 schema 和权限，再交给 Provider。

返回结构统一为 `ok / data / error`；错误包含 code、可显示的 message 和 retryable。设定超时及取消机制，不把原始堆栈、凭据或聊天正文带进提示。

歌曲播放与暂停、切歌是音乐插件的声明命令。面板关闭、固定、尺寸、已读、设置入口是宿主交互，不伪装成音乐或通知命令，也不开放原始 Electron IPC 给插件。

### 4.5 提醒事件与已读

事件包含稳定 eventId、dedupeKey、发生时间、来源、对应页面和可选 readKey。摘要区分不敏感文字与敏感标题/正文，由宿主统一执行隐私、静默、锁屏和字幕开关。

- 显示模式：简要展示标题与最多两行正文，超出省略。
- 隐私模式：只显示来源和“有新消息”等概括，不把正文藏在 DOM 里；适配器获取阶段即进行隐私裁剪。
- 同一事件重复上报不重复提醒；首次连接的历史任务和旧 GPT 通知不当成新消息。
- 当前页真实可见并稳定约 650ms 后视为桌宠内已查看，移除对应未读点；滚动途中、淡出中及后台页不算查看。
- 已查看内容不再次字幕提醒；退出面板后再整理已查看条目，避免阅读过程中页面突然跳动。
- 通知入口只在功能禁用时消失。无未读、权限不足或暂无通知时显示对应空态，不隐藏整个功能。
- 不修改外部聊天的已读状态，不删除 Windows 通知中心的通知。

未读数量与红点由宿主根据事件、readKey 和已读记录计算，不接受插件任意覆盖。已读记录只保存必要标识和时间，不持久保存通知正文。

## 5. 三个内置插件的映射

| 插件 | 可见条件 | 页面与命令 | 必须保留的规则 |
| --- | --- | --- | --- |
| 音乐 | 已启用且有有效播放器会话 | 每个播放器一页；播放、暂停、上一首、下一首按能力显示 | 不监听自己的语音；有封面就显示，无封面用占位；缺失能力时禁用操作 |
| 系统通知 | 已启用，空内容也显示 | 每条通知一页，来源标题吸顶；无通知显示空态 | 铃铛图标、两行摘要、隐私、去重、已读撤点、来源屏蔽 |
| Codex | 已启用且检测到 Codex 运行 | 额度页、最近任务页；此阶段只读 | GPT 图标、额度重置时间、部分失败状态、任务终态只提醒新事件 |

音乐兼容说明写进角色管理器 UI：网易云需要开启 SMTC（此前交流写作 SMCT）；当前验证环境下不提供时长与播放进度，因此显示 `--:--`，不显示虚假的时间线。QQ 音乐按实际报告能力展示控制和进度。

通知兼容说明写进角色管理器 UI：只能接收实际进入 Windows 系统通知通道的消息。当前验证中微信和企业微信没有走该通道，暂不支持，等待官方开放或进入系统通道。不能把托盘红点误报成已经支持；QQ、手机连接等也按实际接收结果显示状态，不保证所有版本都兼容。

Codex 适配器沿用已验证的本机只读链路，不新增启动任务、模型调用、账户修改或凭据读取权限。检测应排除本工具自己启动的服务，避免把采集进程当成用户正在使用 Codex。

## 6. UI 与角色管理器

菜单入口由注册表生成；已启用但暂不可见的插件仍能在角色管理器查看状态和原因。当前顺序先保持音乐、通知、Codex，设置按钮固定在末尾，不参与前面入口的滚动。

内容浏览统一为“页内滚动优先、到边界后进入下一页、滚动结束平滑吸附”。标题在当前页面吸顶，切到下一页时同步换标题。不以一次滚轮事件立即切页，避免恢复生硬翻页。

角色管理器保留两处用途，但共享同一注册表和启用状态：

- 功能页：全局隐私、字幕、静默、动画、悬停延迟、面板尺寸，以及常用插件开关。
- 插件页：插件名称、版本、来源、开关、运行状态、所需能力、自己的设置、兼容说明、失败原因和重启入口。

设置优先采用宿主生成的开关、单选、数值、文本和列表，统一校验与保存。不允许插件直接操作角色配置文件。系统通知访问授权仍由明确的用户操作触发；安装或启用不等于静默完成系统授权。

透明度、配色等未来主题项由宿主管理，插件不能独立再加一套互相冲突的主题系统。

## 7. 权限、故障和后续开放

建议能力划分：

| 能力 | 默认使用者 | 约束 |
| --- | --- | --- |
| media.read / media.control | 音乐 | 只访问允许的媒体会话，控制需校验当前会话及操作能力 |
| notifications.read | 系统通知 | 受 Windows 授权、隐私模式、来源屏蔽共同限制 |
| codex.read | Codex | 只读状态与已验证信息，不提供账户密钥或任务执行入口 |
| ui.reminders | 通知、Codex | 宿主决定展示、去重、限频和已读 |
| storage.own | 有存储需求的插件 | 插件 ID 独立空间、大小限制、无跨插件路径访问 |

开机启动、角色窗口、全盘文件、任意 shell、原始网络和任意 IPC 不作为默认插件能力。未来笔记或 AI 插件如需文件、网络及数据库权限，应增加单独的、可解释且可撤销的能力。

内置插件是受信任应用代码，可以先使用宿主内的轻量 Provider；平台桥接仍由受控进程承载。统一接口和权限清单本身不是不可信代码的安全沙箱，不能因此直接加载别人提供的 Node.js 文件。

第三方开放前另行验证执行隔离、受控能力通信、资源限制、包路径检查、版本兼容和卸载清理。独立进程首先解决故障隔离，不能单独作为“恶意插件无法访问本机”的保证。

一个插件故障只使自己的入口或卡片显示错误，角色和其他插件继续工作。限制发布频率、页面数量、消息大小、资产大小及调用时长；具体限值根据现有数据和性能测试确定，不能使当前通知容量突然缩水。日志仅记录 ID、状态、错误码和耗时。

## 8. 设置与历史数据迁移

建议继续使用 `feature-settings.json`，升级为带 schemaVersion 的第二版结构，内部包含 global 和 plugins 两部分，避免同时维护两份启用状态。

```text
schemaVersion: 2
global: 现有隐私、字幕、静默、动画、延迟、面板宽高
plugins:
  workshop.music: enabled + configVersion + config
  workshop.notifications: enabled + configVersion + config（含来源屏蔽）
  workshop.codex: enabled + configVersion + config
```

旧 music、notifications、codex 开关映射为对应插件 enabled，默认值保持原样。角色、预览、语音与开机启动配置不迁移、不覆盖。

迁移前备份，写入经过校验的临时文件后替换；迁移必须可重复执行，失败则保留旧文件并报告原因。识别不支持的新 schema 时不能擅自覆盖。未知但合法的插件配置保留，插件升级自行通过受控配置迁移处理。

现有 `notification-read.json` 中的 ID 与创建时间映射为通知插件的命名空间 readKey；新记录由宿主统一存入 `plugin-read-state.json`。迁移过程不得重放旧消息，不将正文写入新文件。设置和已读迁移分别记录完成状态，并保证中途中断后可恢复。

## 9. 实施步骤（本轮确认后才开始）

1. 确认本草案的范围、契约、权限和 UI 规则，形成接口清单与测试用数据。
2. 实现注册表、生命周期、状态校验与能力代理；为现有 Windows 桥接和 Codex 服务添加受控包装，不先重写已经验证的协议。
3. 将三个现有功能迁移为内置 Provider，移除宿主中的专用数据路由和硬编码功能分支。
4. 菜单与角色管理器改为注册表驱动，复用现有视觉与分页实现；补齐兼容说明、诊断与禁用清理。
5. 实现设置与已读迁移，完成回归、故障、隐私和性能验证。用一个仅用于测试的第四插件证明无需修改主菜单即可扩展，不借此扩大正式功能范围。
6. 完成实际使用验收，确认接口一致后冻结 apiVersion 1。最后再撰写插件开发手册、样例和开放计划；手册只写真实存在且已验证的接口。

全部实现和验收在 dev/v3 完成。本轮不提交发布、不修改 GitHub、不改已有 v3.1.2 标签。

## 10. 验收标准

- 三个插件通过同一套清单、生命周期、状态、命令和事件接口；通用菜单与设置中不再硬编码三种 ID。
- 添加测试插件只需注册清单和 Provider，现有菜单布局、分页逻辑和设置开关无须新增分支。
- 重复打开、悬停、固定、淡入淡出、边缘缩放、页内滚动与跨页吸附均保持正常；刷新不打断当前阅读。
- 通知查看后撤点但入口保留，隐私裁剪和来源屏蔽有效，升级不重复提醒旧消息，系统通知本身不被修改。
- QQ 与网易云按已验证能力工作，自身语音不被监听，网易云未知时长显示占位，缺失封面不产生破图。
- Codex 额度未知或局部读取失败有明确状态，历史终态不重放，新终态只提示一次。
- 禁用任意插件立即停止其工作；共享适配器不误停其他插件；全部禁用后相关采集进程退出。
- 拒绝越权命令、错误参数、伪造插件身份和无效页面数据；禁用后的异步回调不能恢复入口或触发字幕。
- 旧设置、已读和角色数据不丢失；迁移失败有可恢复路径；日志和持久化记录不泄漏聊天正文或凭据。

## 11. 需要最终确认的三项决定

1. 范围：先插件化三个扩展功能，角色和开机启动等核心能力不拆；第三方安装与市场暂不随版本交付。
2. 界面：插件提供声明式页面与数据，宿主统一渲染；先不开放插件自带 HTML/CSS，保证现有简洁风格与交互一致。
